# Phase 3.1 — Streaming 治理语义设计（语义先行）

本文档回答 Streaming 世界的“第一性问题”（非技术问题），用于稳定约束后续实现（quota/metering/policy/provider handler）。

## 目标

- 给出清晰且可落地的 Streaming 成功/失败/计费/配额语义。
- 给出可被代码直接映射的事件点（request start / provider connect / first chunk / end / client disconnect）。
- 不追求完美，只追求**明确**与**一致**。

## 范围与术语

- **Request**：一次用户 API 请求（如 `/v1/chat/completions`）。
- **Provider**：上游模型服务。
- **Chunk**：Streaming 模式下的一段增量响应（SSE 事件或等价形式）。
- **Token**：模型输出计量单位。实现上可能用 `usage` 或 chunk 增量估算。
- **Quota（配额）**：平台侧对请求/Token 消耗的预算控制（事前/事中治理）。
- **Metering（计量）**：平台侧对已发生消耗的记录（事后统计/计费）。

## 1️⃣ 什么叫“一次请求成功”？

Streaming 下，“成功”至少存在两个层级，需要明确：

### A. 传输层成功（Transport Success）

满足：

- Policy 允许（未被事前拒绝）。
- Gateway 与 Provider 建连成功并返回可读响应。
- Gateway 向客户端返回 HTTP 200 并开始写入响应体。

> 说明：仅 provider 返回 200 但没有任何响应体写入，不视为 Streaming 成功起点（对用户体验和计量都不稳定）。

### B. 生成层成功（Generation Success）

满足：

- Gateway **至少向客户端成功写出并 flush 过一个有效 chunk**（可称为 **first chunk** / **first byte**）。

> 这定义了 Streaming 世界里“用户确实拿到了东西”的最低成功标准。

### C. 完成层成功（Completion Success）

满足：

- 流正常结束（EOF 或显式终止），且上游未返回中途错误。
- 对于 OpenAI 语义：最终 `finish_reason=stop`（或等价的正常结束原因）。

> 说明：Completion Success 不是计费/配额的唯一依据，但它可用于 SLA/可观测性指标（成功率、尾延迟）。

## 2️⃣ Token 在什么时候“被确认消耗”？

Streaming 下建议采用“**确认点**”概念：token 只有在到达某个可观测事件点后才被认为**已发生**。

### 建议的确认点：以“写出到客户端”为准（Client-Delivered Confirm）

原则：平台只为“成功交付给客户端的内容”负责计量，而不为“尝试生成的内容”负责。

- **确认消耗点**：Gateway 成功向客户端写出并 flush 某个 chunk 后。
- **含义**：
  - 在确认点之前发生的失败，不计入 token 消耗。
  - 在确认点之后发生的失败，计入已确认部分（已交付给客户端）。

理由：

- 该事件点可在网关侧稳定观测（比 provider 侧内部 token 更可控）。
- 与用户体验一致：用户看到的内容才算“已交付”。

> 备注：这并不要求“每个 token 都精确确认”。实现上可以按 chunk 聚合确认。

## 3️⃣ 哪些失败不应计费？

原则：**事前拒绝不计费；未产生交付不计费；已交付的部分计费**。

下面给出初版治理语义表。

## Streaming 治理语义表（初版）

| 场景                                            | 是否消耗配额      | 是否计入 metering | 说明                                             |
| ----------------------------------------------- | ----------------- | ----------------- | ------------------------------------------------ |
| Policy 事前拒绝                                 | ❌                | ❌                | 未执行 provider 调用；直接返回 deny              |
| Provider 建连失败（DNS/TCP/TLS/超时/握手失败）  | ❌                | ❌                | 未开始生成/未交付                                |
| Provider 返回非 2xx（含 4xx/5xx）且未产生 chunk | ❌                | ❌                | 视为调用失败；建议记录失败事件但不计 token       |
| Provider 返回 2xx，但在首个 chunk 前断流/报错   | ❌                | ❌                | “成功起点”未发生                                 |
| Provider 返回首个 chunk（成功写出/flush）       | ⚠️                | ⚠️                | 可视为成功起点；后续按已交付部分累计             |
| 流正常结束（finish_reason=stop 或等价）         | ✅                | ✅                | 全量计费（以已交付 token 为准）                  |
| Provider 中途 5xx/断流（已发生首 chunk）        | ✅（已确认部分）  | ✅（已确认部分）  | 不追溯撤销已交付；未交付部分不计                 |
| 客户端中途断开（已发生首 chunk）                | ✅（已确认部分）  | ✅（已确认部分）  | **建议算**（平台友好）：已交付部分算；未交付不算 |
| 客户端中途断开（首 chunk 前）                   | ❌                | ❌                | 未交付                                           |
| 网关超时中断                                    | ❌ / ⚠️（可配置） | ❌ / ⚠️（可配置） | 若超时发生在首 chunk 后，建议同“已确认部分计费”  |

解释：

- 表中“✅（已确认部分）”表示：只对已经过“确认消耗点”的部分计入。
- “⚠️”表示：这是一个关键事件点，但是否立刻扣配额/写 metering 取决于实现策略（可在 Phase 3.2+ 落地）。

## 4️⃣ 治理是否可以旁路？

需要明确“哪些组件失败/关闭时，系统是否继续提供服务”。建议如下：

### A. Streaming 是否允许在 quota 关闭时继续？

- **允许**。
- Quota 是治理能力，关闭意味着“不做预算拦截”，但不应阻断业务可用性。

### B. Metering 失败是否影响响应？

- **不影响响应**（旁路）。
- Metering 属于事后记录：失败应降级为日志/告警，不应让用户请求失败（否则会放大故障）。

### C. Policy 是否允许旁路？

- **不允许**。
- Policy 是请求入口的硬门禁：一旦评估为 deny，必须直接拒绝。

## 建议的稳定口径（便于后续实现）

- **成功起点**：首个 chunk 成功写出并 flush。
- **确认消耗点**：每次 chunk 写出并 flush 后确认（可按 chunk 聚合 token）。
- **计费/配额粒度**：
  - 非 streaming：请求结束时根据 usage 结算。
  - streaming：按“已确认部分”累计；流结束时做最终结算/补偿。
- **客户端断开**：不回滚已确认消耗。
- **治理旁路**：metering 旁路；quota 可关闭；policy 不可旁路。

- 不讨论具体错误码/HTTP 语义细节落地（但会要求一致）。
- 不写任何代码实现。
